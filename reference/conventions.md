# Conventions — mock-ui

This file doubles as the review-loop checklist: reviewers score every rule id below against
the group's files and cite ids (BPnn/APnn) in findings. Items tagged `[scan]` are mechanical
grep-shaped rules covered by `scripts/verify_pages.sh` — reviewers skip them and spend judgment
on the rest.

**It extends the project's skills, it does not replace them.** `code-ui` owns how UI is written
here (reuse, the four states, accessibility, messages, layout that does not shift) and `web`
owns where files live, the theme contract, and the data boundary. What lives here is what those
two do not cover: Next 16 route mechanics, the mock-data boundary, and the AI-slop rules. Where
a rule below and one of those skills disagree, **the skill wins** — it has lint rules and tests
behind it, and this file does not.

## Design findings (1–5)

1. Next 16 `error.tsx` receives `{ error, retry }` — the pre-16 `reset` prop is gone
   (10-error-handling.md).
2. `PageProps`/`LayoutProps` are globally generated types, and here they are generated by
   `next typegen` inside `apps/web`'s `codegen` script, which `turbo.json` declares a dependency
   of `typecheck`, `lint` and every test task. So it is **not** something to remember: run the
   gate and the types exist. A missing `PageProps` means codegen has not run, never that the
   type should be hand-written or imported.
3. The route groups live under the ONE existing root layout, `apps/web/src/app/layout.tsx` —
   never a second root layout. It owns `<html>`/`<body>`, the two `next/font` variables and the
   `ThemeProvider`; a group layout that re-declares any of those breaks theming or forces a full
   page reload on cross-area links.
4. Token values live in `apps/web/src/styles/theme.css`; the `@theme inline` mapping lives in
   `apps/web/src/app/globals.css`. `shadcn add` appends both to `globals.css` when a component
   needs a new token — keep the mapping line there and **move the values down into theme.css**,
   in both `:root` and `.dark`. Leaving them in globals.css puts them after the `@import` of
   theme.css, where they win on cascade order, and the file you edit afterwards is the one that
   does nothing. `src/styles/theme.test.ts` fails the half of this it can see.
5. Mock-data accessors are async functions, so `loading.tsx` and Suspense render truthfully and
   the later swap to `graphqlFetch` touches only `src/lib/mock-data.ts` — never a page.

## Best practices — DO / DON'T

### Server/client component boundaries (05-server-and-client-components.md)

- BP1. Pages and layouts stay Server Components: no `"use client"` in any page.tsx, layout.tsx,
  loading.tsx, or not-found.tsx. Interactivity lives in leaf components under `src/components`.
- BP2. `"use client"` only on the smallest interactive leaf (a form wrapper, a menu trigger, a
  dialog) — never on a page section that is mostly static.
- BP3. `src/lib/mock-data.ts` starts with `import "server-only"` so a client import fails at
  build time; no client file imports it.
- BP4. Data crosses the boundary as serializable props, or as children slots for server-rendered
  content inside a client shell. Never fetch initial page data in `useEffect`.
- BP5. `error.tsx` and `global-error.tsx` begin with `"use client"` — the only route files that
  do (10-error-handling.md).

### Awaited params/searchParams and typing (page.md, layout.md, dynamic-routes.md)

- BP6. `params` and `searchParams` are Promises: every access is `await props.params` (or
  `use()` in a client page). A synchronous `params.` access is a violation.
- BP7. Type pages `PageProps<'/route/[param]'>` and layouts `LayoutProps<'/route'>` with the
  route literal — global helpers, no import (design finding 2).
- BP8. Read `searchParams` only in page.tsx, never in layout.tsx — layouts do not re-render and
  have no searchParams. Client-side-only filtering uses `useSearchParams`.
- BP9. Param values are `string | string[] | undefined`: parse them and call `notFound()` when
  the entity does not exist, before any suspending await.

### Data fetching, Suspense, loading.tsx (loading.md)

- BP10. Fetch in the async server page (or an async server child) by awaiting the mock-data
  accessors; pages are `async function`.
- BP11. Every segment that awaits data has a `loading.tsx` skeleton mirroring the real page shape
  (shadcn `Skeleton` in the same card/table/list layout) — never a bare spinner or a
  "Loading…" string.
- BP12. Layouts never fetch uncached data: it blocks `loading.tsx` from showing.
- BP13. Independent slow regions on one page get their own `<Suspense fallback={…}>` instead of
  one page-wide await chain.
- BP14. When `generateMetadata` and the page need the same record, wrap the accessor in React
  `cache()` so it runs once.

### error.tsx / not-found.tsx (10-error-handling.md)

- BP15. Each route group has an `error.tsx` whose props are `{ error, retry }` (design finding
  1); a `reset` prop is a bug.
- BP16. Expected failures — validation, sold out, expired — are returned as action-state values,
  never thrown. Thrown errors are for genuine bugs, and `error.tsx` is what catches them.
- BP17. Detail routes have a sibling `not-found.tsx`, and the page calls `notFound()` on missing
  ids.

### Route groups, layouts, nav (route-groups.md, layout.md)

- BP18. Exactly one root layout owns `<html>`/`<body>`; group layouts return plain wrappers
  (design finding 3).
- BP19. Each group layout carries that area's shell — header, nav, footer. No per-page
  copy-pasted nav bars.
- BP20. No two routes resolve to the same URL path. This is a build error, and the usual cause is
  a new `(group)/page.tsx` beside a surviving `src/app/page.tsx` (see BP58).
- BP21. Internal navigation uses `<Link>` from `next/link`; `<a href="/…">` is a violation, and
  `router.push` is only for a real programmatic redirect.
- BP22. Every page exports `metadata` or `generateMetadata` with a distinct title; the root
  layout sets `title.template`; no manual `<head>`/`<title>` anywhere.

### Forms via server actions (07-mutating-data.md, and `code-ui`)

- BP23. Mutations are server actions in `"use server"` files (`src/app/**/actions.ts`), invoked
  through `<form action={…}>`. No `onClick` fetch, and no route handler for a form post.
- BP24. Every server action starts with a session check — plus a row-ownership check for a
  customer resource. An action is reachable by direct POST, so the guard lives in the action even
  at mock stage, and a layout guard is navigation rather than security.
- BP25. An action used with `useActionState` takes `(prevState, formData)` and returns a typed
  state declared beside it — e.g.
  `{ status: "idle" | "error" | "success"; message?: string; fieldErrors?: Record<string, string> }`.
  Never `any`.
- BP26. The submit button reflects pending state and never goes silent: disabled while pending,
  with visible pending text. Where the form validates client-side, it is disabled until valid too.
- BP27. Inputs carry `name` attributes read via `formData.get()`, and every input has a
  `<Label htmlFor>` matching its `id`. A placeholder is never the only label.
- BP28. On success: `revalidatePath()` (or `router.refresh()`) and then `redirect()` — in that
  order, because `redirect` throws and code after it never runs. A `redirect()` inside a `try`
  is a silent no-op (`web` skill).
- BP29. Action messages render where they belong, per `code-ui`: field errors under their field,
  whole-attempt failures in one form-level alert **at the top of the form**. Field message slots
  reserve their line (`min-h-[1lh]`) so nothing moves when a message appears; the form-level
  alert does not reserve space, because a block has no single height to hold. Errors are
  `role="alert"`, confirmations `role="status"` — shadcn's `Alert` hardcodes `role="alert"`, so a
  confirmation overrides it.
- BP53. **No form library, and no native validation bubbles.** The `<form>` gets `noValidate`
  and blank/malformed input is checked in the browser with plain state, so there is no round
  trip; the server owns length, uniqueness and credentials, and stays the source of truth
  (BP16, BP24, BP25 unchanged). Keep semantic input types (`email`, `tel`) — `noValidate` strips
  their validation, not their mobile-keyboard semantics. Never render a raw server error string:
  map its `code` to your own copy and log anything unmapped. Clear a field's error when that
  field is edited, or it stays red while the user fixes it. Exemplar:
  `apps/web/src/components/auth-panel.tsx`. Installing react-hook-form or zod for a mock form is
  out of scope — it is a second form philosophy in an app that already has one.

### Accessibility

- BP30. Exactly one `<h1>` per page; heading levels never skip.
- BP31. Every input has a programmatically associated label; an invalid input gets
  `aria-invalid` plus `aria-describedby` pointing at its message.
- BP32. Icon-only buttons have `aria-label` or an `sr-only` span (see `ModeToggle`); decorative
  lucide icons get `aria-hidden="true"`.
- BP33. Group layouts render landmarks: `<header>`, `<nav aria-label="…">`, one `<main>` around
  page content.
- BP34. Status is never colour-only: a Badge colour is paired with literal text ("Sold out",
  "3 left", "Expires 12 Sep").
- BP35. No `outline-none` on an interactive element without a `focus-visible:` replacement. The
  vendored primitives already ship one — do not strip it.
- BP36. Tabular data uses a real `<Table>` (table/th semantics), not a div grid; the current
  page's nav link gets `aria-current="page"`.
- BP50. Cards are not whole-clickable: the title is a normal `<Link>` and the footer action is a
  Button-rendered link, styled the same on every sibling card. Never a card-level `onClick` on a
  div, and never nested interactive elements. The stretched-link pattern (a `relative` card, ONE
  title link with `after:absolute after:inset-0`, secondary controls raised with `relative z-10`)
  is the approved technique if whole-card targets are ever wanted — but adopting it is an
  app-wide decision applied to every card grid at once, never piecemeal.
- BP51. A short, non-destructive, context-returning action may render as a URL-driven dialog via
  intercepting + parallel routes — never as a client-state-only popup: the full page keeps its
  canonical URL (deep links, refresh, no-JS), the group layout gains a `@modal` slot with a null
  `default.tsx`, and `@modal/(.)<path>/page.tsx` renders the SAME form component inside a client
  dialog shell that closes with `router.back()`. Two defences are needed for its loading state,
  because on unprefetched re-entry the router applies the LAYOUT-level loading boundary to the
  slot: (a) the intercepted page is synchronous — it returns the dialog shell immediately and
  suspends only inside it; (b) the layout wraps the slot in a container that hides children
  lacking `data-modal-chrome` (`[&>*:not([data-modal-chrome])]:hidden`), so only the leaked
  page-shaped fallback is suppressed. Consequential, multi-step, or externally-entered flows
  (checkout, login, set-password, cancellation) stay full pages. Never fork the copy or the form
  between page and dialog.
- BP52. **No invention.** Every domain noun, form field, price rule, status and copy fact traces
  to the PRD, the data model, the run's inventory, or `.cache/mock-ui/facts.md`. Capture forms
  mirror their entity's columns exactly — names, required/optional, nullability pairings — and a
  required column missing from a form and a field the spec never asked for are equally findings.
  Anything on the PRD's not-in-scope list must not appear. When the spec is silent on a fact the
  UI needs, flag the gap; never fill it from a plausible prior.
- BP54. UI copy is not prose: every descriptive slot — page lede, `CardDescription`,
  `DialogDescription`, `AlertDescription`, empty state — holds ONE short sentence. Long-form
  paragraphs belong only where the content genuinely is an article. Required or dense information
  that cannot be cut changes UI PATTERN, not sentence length: a scannable list, Badges, a
  definition row, a collapsible, a footnote, or its own element beside the message — never
  another clause bolted onto an existing paragraph. Pick the pattern by how loud the content
  deserves to be: fine print is a FOOTNOTE — small muted type under a hairline rule, no icons,
  because an icon per line reads as emphasis on text whose whole job is to be available rather
  than prominent. State a fact ONCE per screen: terms render at the point of commitment, beside
  the submit control, and the success state is a short receipt with the terms persisting as its
  SIBLING rather than restated inside it. Message strings stay short enough to set on one line,
  because a wrapped message defeats the reserved slot (BP29).
- BP55. A heading is state when the screen's outcome changes it. A dialog still titled "Join the
  waiting list" above a success receipt reads as an unfinished task, so the component that owns
  the state owns the heading — not the shell around it. Where a shell normally supplies the
  title, make that prop optional and let stateful content render its own, remembering that a
  Dialog needs a `DialogTitle` in EVERY branch, Suspense fallback and not-found included, or it
  loses its accessible name. Put `aria-live` on the heading, not the panel root, or every field
  error re-announces the whole form.
- BP56. Anchor a dialog whose content changes height; do not centre it. The default
  `top-1/2 -translate-y-1/2` re-centres when a form collapses into a receipt, dropping the
  heading a hundred pixels down the viewport. A proportional top offset with a max height
  (`top-[12dvh] max-h-[76dvh] translate-y-0 overflow-y-auto`) holds the heading still, lets the
  body shrink upward, and still scrolls on short viewports.

### shadcn/ui usage

- BP37. Primitives import from `@/components/ui/*` only; never hand-roll a control a vendored
  primitive covers.
- BP38. Feature components are composed under `src/components/<area>/`; page.tsx stays thin —
  await data, compose components, pass props.
- BP39. Conditional classes go through `cn()` from `@/lib/utils`; no template-string class
  concatenation.
- BP40. Visual variants use the primitive's own `variant`/`size` props, not className soup at the
  call site. A genuinely new variant is a wrapper under `src/components/<area>/`, never an edit
  to the ui file.
- BP41. `src/components/ui/**` is a vendored checkout of the shadcn registry, owned by the CLI.
  No hand edits, ever — an edit there is a fork you now maintain, and the next `shadcn add`
  silently takes it back. The setup script never passes `--overwrite` for a component that is
  already present, but that is a safety property, not permission.
- BP59. `Button` is Base UI, so composition is `render={<Link … />}`, **not** `asChild`, and
  rendering anything that is not a `<button>` needs `nativeButton={false}` alongside it — without
  it the primitive warns that it applied native button semantics to an element that has none.

### The shell, the breakpoints, and the mock's own furniture

The mock owes the final layout minus design and minus the backend. These eight rules are what
that sentence costs: every one of them names a structural decision that is cheap to make once,
here, and expensive to discover missing three slices later.

- BP61. **One shell module, and it owns the page heading.** The container, the area header, the
  nav, the footer, the page heading, the section heading and the empty state live once, under
  `src/components/shell/`, and every group layout and page composes them. A group layout adds its
  own nav items and its own guard and nothing else. `<h1>` appears in exactly ONE component —
  the page heading — and every screen, including `not-found` and `error`, renders it. Two areas
  that each hand-roll a header do not look different on purpose; they look different because
  nobody compared them, and by the time anyone does, thirty pages depend on both.
- BP62. **Every screen decides its phone layout.** The shell contract fixes the behaviour of each
  pattern — card grid, data table, definition list, form, header, dialog — and each screen
  applies it. A file that lays out columns or renders a table and carries no breakpoint at all
  has not decided; it has inherited whatever the desktop markup does when squeezed, which for a
  wide table is a sideways scroll nobody chose. Deciding is cheap here and expensive later,
  because the slice that replaces the data has no mandate to redesign the screen.
- BP63. **The design seam is used uniformly or not at all.** Whatever hook the app leaves for the
  design pass — a heading-font token, a tracking scale, a surface variant — is either on every
  screen of every group or on none. A seam wired in two areas out of three is worse than no seam:
  it does nothing today, so nothing catches it, and it silently omits an area on the day the
  design pass finally gives it a value.
- BP64. **The mock's annotations are one component behind one flag.** Open questions shown on
  screen (BP52) are real value — a form that cannot be filled in is the point — but they are
  furniture that ships out, so they render through ONE component in ONE mock-only directory,
  gated by ONE flag. Never a second copy per area. With the flag off the screen must be the
  layout that will ship; deleting the annotations at the end must be deleting a directory and
  fixing imports, never editing thirty pages by hand.
- BP65. **Scaffold demo UI is removed, not parked.** In greenfield mode, whatever the scaffold
  shipped to prove its own wiring — a diagnostics panel, a "test item" link, a sample page — is
  deleted rather than moved into the product's header, footer or sidebar. What is genuinely real
  is re-homed into the product screen that owns that job (pages.md, disposition rulings). A
  doc-owned file carries its reasoned `docs-check.ignore` line with it (BP58). In extension mode
  this rule is inert: there is no scaffold UI left to rule on, and the existing product shell is
  law.
- BP66. **A route another skill owns keeps its surface and still gets its page.** The embedded
  widget, the callback handler and the secret exchange are not rewritten and not re-mocked. The
  page around them is: the summary of what is being committed to, the totals, whatever identity
  the flow captures, the terms at the point of commitment, the shell, and the screen the flow
  returns to. The owned route also sits inside a group's shell like every other screen, so a
  visitor mid-flow does not lose the site's header and nav.
- BP67. **Root fallbacks exist.** `src/app/not-found.tsx` and `src/app/global-error.tsx` are
  written and render inside the shell. An unknown URL and a layout-level crash are two real
  screens of the product, and they are the two nobody navigates to on purpose.
- BP68. **A dialog that owns a mutation survives a refresh, or it is a page.** BP51's URL-driven
  pattern is the way to make a short, non-destructive action a dialog. A client-state-only dialog
  is acceptable ONLY for a confirmation of a single action whose context is fully on the page
  behind it, and it must restate what it is confirming. Anything with fields, steps, or a state
  the user would be upset to retype is a page.

### Theming / design tokens

- BP42. `[scan]` Only semantic token classes in JSX: `bg-background`, `bg-card`,
  `text-foreground`, `text-muted-foreground`, `border-border`, `bg-primary`, `text-destructive`.
  A raw palette utility (`text-red-600`, `-slate-`, `-zinc-`, `-gray-`) fails lint via
  `no-restricted-syntax` in `apps/web/eslint.config.mjs`, in both string and template-literal
  classNames.
- BP43. No hex/rgb/oklch literal in `className` or `style={}`. Every colour value lives in
  `src/styles/theme.css`, which is what makes a re-theme a one-file edit.
- BP44. Dark mode is the `.dark` block redefining the same variables, never
  `prefers-color-scheme` — a media query cannot be toggled. Component files carry no scattered
  `dark:` overrides; the target is zero in `src/components` and `src/app`.
- BP45. A new token means two edits: the `@theme inline` mapping in `globals.css` and the value
  in `theme.css` under BOTH `:root` and `.dark` (design finding 4). `src/styles/theme.test.ts`
  asserts exactly this — every mapped token declared, every colour token with a dark value, and
  the dark block overriding nothing the light block never declared.
- BP46. Radius comes from the `--radius` token and the Tailwind scale; no arbitrary values
  (`w-[437px]`, `rounded-[13px]`) without a justifying comment.

### Mock-data isolation

- BP47. Domain interfaces live once in `src/lib/types.ts`; no inline or anonymous data shapes in
  pages.
- BP48. All mock data sits in the single `src/lib/mock-data.ts` module exposing async accessors.
  Pages await accessors; components receive typed props and never import mock-data.
- BP49. Mock records are realistic and cover edge states on purpose — the sold-out one, the
  nearly-full one, the expiring one, the pending request, the past record with a receipt — so
  every UI state in the inventory is demonstrable.
- BP57. **The mock stands in for the API, not for the database.** `mock-data.ts` never imports
  `@nanostore/db`, never imports `stripe`, and never reaches a network: web reaches data only
  through GraphQL, and the dependency graph is what enforces the architecture (`web` skill). Each
  accessor is shaped like the `graphqlFetch` call that will replace it — async, awaited in a
  server component, returning exactly the fields the screen renders — so a slice swaps one
  function body and no page changes.

### The plan of record

- BP58. `pnpm docs:check` compares `docs/2026-08-08-setup` against the working tree file by file,
  and it runs inside `pnpm verify`. A file the plan claims — `src/app/page.tsx`,
  `src/app/layout.tsx`, `globals.css` among them — cannot be replaced, moved or deleted without
  either updating the plan or appending a reasoned line to `scripts/docs-check.ignore`, in that
  file's own format: the path, then a comment saying why, then the sentence that says when the
  line should be deleted. A mock replacing a scaffold page is the ignore line, not a plan
  rewrite: the plan records how the scaffold was built, and that history did not change.
- BP60. `export const dynamic` is gone in Next 16 — `connection()` replaces it, and
  `graphqlFetch` already calls it at the boundary. A mock page needs neither: mock accessors
  read no Worker bindings, so pages may prerender, and adding a prerender opt-out per page is
  the habit that survives into the real slices and disables static rendering everywhere.

## AI UI anti-patterns to avoid (impeccable.style)

Source: impeccable.style (pbakaus/impeccable) deterministic slop rules, phrased as greppable
DON'Ts. `[scan]` = covered by `npx impeccable detect` in `verify_pages.sh`; reviewers skip those.

### Visual details

- AP1. `[scan]` No side-tab accent borders: `border-l-4`/`border-l-2` plus a coloured border
  class on a card — the most recognizable tell of AI-generated UI.
- AP2. `[scan]` No thick accent border on a rounded card (coloured `border-2`+ with `rounded-*`).
- AP3. `[scan]` No decorative glassmorphism: `backdrop-blur` plus translucent surfaces or glow
  borders, unless solving a real layering problem.
- AP4. `[scan]` No hairline border paired with a wide diffuse shadow (`border` plus
  `shadow-xl`/`shadow-2xl` on one card).
- AP5. `[scan]` No decorative grid-line or repeating-gradient-stripe backgrounds without a
  canvas or measurement purpose.
- AP6. `[scan]` No extreme rounding: `rounded-3xl`+ on small cards or inputs, and no giving every
  element the same radius.
- AP7. No hand-coded decorative SVG scenes or mascots, and no hero assembled from generic SVG
  shapes.

### Colour & contrast

- AP8. `[scan]` No purple/violet gradients or cyan-on-dark accents (`from-purple`, `from-violet`,
  `from-indigo`, `to-cyan`).
- AP9. `[scan]` No gradient text: `bg-clip-text text-transparent` anywhere.
- AP10. `[scan]` No dark surface with a glowing coloured box-shadow.
- AP11. `[scan]` No radial-gradient halo or spotlight glow behind a section.
- AP12. No cream/beige "tasteful AI default" page background — the page background is the
  `bg-background` token, unmodified.
- AP13. No grey text on a coloured background (`text-muted-foreground` on `bg-primary`); all text
  meets WCAG AA — 4.5:1 body, 3:1 large.

### Typography

- AP14. No kicker/eyebrow: a tracked-uppercase mini-label or pill chip above a heading.
- AP15. No icon-in-rounded-tile stacked above a heading — the universal AI feature-card template.
- AP16. No oversized italic serif display hero, and no full-sentence display-size headline
  monopolizing the viewport.
- AP17. No flat hierarchy: adjacent heading and body sizes differ by clear steps.
- AP18. No all-caps body passages, no letter-spacing above 0.05em on body text, no crushed
  negative tracking on display text.
- AP19. No functional text under 11px or body text under 12px; line-height on multi-line text
  ≥ 1.3 (no `leading-none`/`leading-tight` on paragraphs).

### Layout & space

- AP20. No identical card grids — same-sized icon+heading+text cards repeated endlessly. Vary by
  what the data warrants.
- AP21. No hero-metric cliché (big number, tiny label, three supporting stats, gradient accent)
  on a dashboard; stat tiles use plain token styling.
- AP22. No nested cards; flatten with spacing or dividers.
- AP23. No monotonous spacing — one gap value everywhere. Tighter within a group, looser between
  sections.
- AP24. No prose line wider than ~80ch: long text gets `max-w-prose`.
- AP25. No tiny numbered section labels ("01", "02") beside headings.
- AP26. No content flush to edges: containers keep ≥12–16px padding, and nothing forces
  horizontal scroll.
- AP27. No justified text, and no skipped heading levels.

### Motion

- AP28. `[scan]` No pulsing status dots (`animate-pulse` on an indicator), no decorative blinking
  cursors, no auto-scrolling marquees.
- AP29. `[scan]` No bounce or elastic easing, and never animate layout properties — transform and
  opacity only.
- AP30. `[scan]` No image hover transforms (`hover:scale-*`, `hover:rotate-*`).

### Copy & imagery

- AP31. No marketing buzzwords in UI copy — streamline, empower, supercharge, world-class,
  enterprise-grade — no em-dash-heavy body copy, and no repeated identical labels within one card.
- AP32. No `<img>`/`<Image>` with an empty, missing or placeholder `src` shipping as a
  broken-image box.
